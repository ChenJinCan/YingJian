# 自然人像精修纵切 Spec

> 状态：Draft，等待样片与候选引擎评测后冻结

> 工程进展（2026-08-05）：iOS `ios-geometry-retouch-candidate-v4` 在 v3 的受蒙版低频柔化之上增加源图高对比细节保护，避免胡须、眼镜、嘴唇、深皱纹和永久特征被平滑链路抹除，并新增公开候选接缝的合成边缘回归。独立人像清单已在本机实际达到 48 张（36 张单人成人、4 张多人、8 张无人脸），生产源码驱动的运行结果为 36 张应用候选、12 张安全保持、0 个意外结果。`candidate-engineering-v13` 对最终 JPEG 建立独立 baseline/off 恒等、工程可见度、默认/高安全强度与方向一致性、全图变化预算和负向输入零变化门；schema 4 绑定共享 Swift 指标实现，诊断包会从最终文件重算并核对报告。36 张单人全部通过，12 张负向输入逐像素零差。代表样片的局部观察显示低频肤质得到柔化，同时五官、胡须、眼镜、发丝、深皱纹和永久特征仍可辨认，未见明显黑边、光晕或轮廓过锐；但全图像素差无法定位背景或五官泄漏，也不评价“更好看”、自然度和局部 halo。该观察不是匿名盲评，也没有竞品和物理设备对照。公共许可素材只能补充工程回归，不能替代真实用户授权、竞品、五人盲评和物理设备门，也不授权生产入口。

## 1. 为什么先做这个纵切

映见当前已经有照片导入、项目恢复、三个全局色彩参数、Android GLES3 预览和双端单张导出接缝。这些能力证明了移动端图像管线可以运行，但不能证明产品已经提供修图价值。

曝光、对比度和色温只能改变整张图片，无法区分皮肤、五官、头发、人物和背景，也不能在提亮面部时保护高光、在均匀肤色时保留皮肤纹理。继续增加全局滑杆会扩大工具数量，却不会兑现“一张精修，整组好看”。

因此，MVP 的下一个阻断门不是批量导出或更多滤镜，而是一个真实可盲评的自然人像纵切：

> 输入一张普通成人肖像，系统在本地给出克制的人像改善；结果应减少暗沉和不均匀感、改善面部光线、减弱小范围暂时性瑕疵，同时保留皮肤纹理、五官边界、发丝、妆容和身份特征。

如果没有候选链路通过本 Spec 的质量门，映见不能宣称具备“精修”或进入三套推荐、整组迁移和商业化包装。

## 2. 证据与决策状态

### 已确认事实

- 当前 `ImagePipelineV1` 只表达曝光、对比度和色温，不能表达皮肤遮罩、局部光照或纹理分离。
- Android 已具备 GLES3 Texture 预览接缝，Flutter 与原生层可以只传路径、版本化参数和会话状态。
- 竞品 Android 静态样本存在人脸关键点、皮肤/人体分割、LUT、模糊、Shader 和多个端侧推理后端的组合证据；静态证据不证明具体功能的运行路径或最终质量。
- 当前产品原则要求默认本地处理、原图只读、配方可撤销可恢复，并禁止把人脸特征写入普通日志或遥测。

### 待验证假设

- 克制的面部光线、肤色均匀和纹理保护比五官重塑更符合映见首版定位。
- 用户可以通过一个总强度控件得到满意结果，不需要先理解多个专业人像参数。
- 系统 API、自建基础链路或商业 SDK 中至少有一条路线能在目标设备、许可和包体约束内通过质量门。
- 一张人像通过后，同一能力可以作为整组逐张肤色保护和安全补偿的基础，但不能直接证明组图一致性已经成立。

### 本 Spec 不提前决定

- 不提前指定 Apple Vision、MediaPipe、ML Kit、商业 SDK 或自有模型为最终供应商。
- 不因 APK 中出现 GLES、Vulkan、OpenCL、模型名或厂商库，就推断竞品的实际算法或映见应采用相同实现。
- 不在样片盲评前冻结具体磨皮算法、模型、默认强度或商业供应商。

## 3. 用户可见结果合同

### 3.1 首个结果：自然精修

纵切只交付一个经过调校的结果方向“自然精修”，不同时制作三套推荐。它必须包含以下四类改善：

1. **面部光线**：克制提亮阴影和暗沉区域，保护额头、鼻梁、颧骨等已有高光，不把背景同步提亮。
2. **肤色均匀**：减弱局部泛红、偏黄和低频色块，但保留原有肤色、妆容和唇色，不把不同肤色统一成同一颜色。
3. **纹理保护型平滑**：减弱小尺度粗糙感和高 ISO 彩噪，同时保留毛孔趋势、面部轮廓、眉毛、睫毛、发际线、胡须和痣等稳定身份细节。
4. **轻度暂时性瑕疵减弱**：只在候选能力能够稳定区分时处理小范围痘印或短期瑕疵；无法稳定区分痣、雀斑和身份特征时必须跳过，而不是冒险删除。

### 3.2 用户控制

- 默认只暴露一个 `自然精修强度`，范围 `0...100`，`0` 必须严格等价于关闭人像处理。
- 初始推荐强度、最高安全强度和内部子参数比例均属于样片调校结果，当前不写死为产品事实。
- 用户可以长按或使用明确按钮查看完整原图对比。
- 人像调整形成可撤销的语义步骤；关闭后再次开启应得到确定性相同结果。
- 单张项目直接显示当前照片；未来多图项目的人像结果默认属于逐张补偿，不自动修改整组共享风格。

### 3.3 明确禁止的结果

- 改变脸型、眼睛大小、鼻形、嘴形、身材或头身比例。
- 擅自添加妆容、改变唇色、增白牙齿或眼白。
- 将皮肤处理成无纹理塑料表面。
- 在发际线、眉毛、鼻翼、嘴唇、眼镜、胡须或人脸边缘产生光晕、漏抹和锯齿。
- 将背景、衣服、头发、宠物或其他非皮肤区域当作皮肤处理。
- 因检测失败而阻止基础编辑、项目恢复或导出。

## 4. 纵切范围

### P0 必须具备

- 单张、成人、静态 JPEG/HEIC 人像。
- 正脸与轻度侧脸；单人是首要质量路径，多人必须安全降级。
- 人脸/人物或皮肤适用性分析。
- 原生会话内的软遮罩与参数更新，不把完整遮罩或人脸特征传到 Flutter。
- 面部光线、肤色均匀和纹理保护型平滑。
- Android GLES3 代理图预览；iOS 候选路径必须通过同一效果合同后才能称双端完成。
- 从应用持有的只读原图重新执行同一有效配方。
- 无人脸、低置信度、遮挡、过小人脸和能力不可用的明确降级。

### P0 可选，需由样片证明收益

- 轻度暂时性瑕疵减弱。
- 对高 ISO 人像增加受控的肤色区域色噪抑制。
- 多人照片按每张脸独立计算安全强度。

### 本纵切明确不做

- 五官重塑、瘦脸、大眼、美体、妆容、牙齿和眼白美化。
- 实时相机、视频、Live Photo。
- 云端人像生成、换脸、写真、身份迁移。
- 手动画笔、手工皮肤选区和复杂局部蒙版编辑器。
- 儿童人像专项效果与年龄推断。
- 三套推荐、整组迁移和批量导出；这些只在本纵切通过后接入。

## 5. 效果处理模型

### 5.1 处理顺序

候选实现必须遵守相同的高层语义，具体 Shader 或模型可以替换：

```text
输入方向与 sRGB 规范化
  → 受控尺寸分析代理图
  → 人脸/人物/皮肤适用性分析
  → 软遮罩清理、羽化和边界保护
  → 基础光色校正
  → 面部低频光线修正
  → 肤色低频均匀
  → 纹理保护型平滑
  → 可选的安全瑕疵减弱
  → 细节回注与强度混合
  → 预览 Texture 或原图导出
```

处理顺序是效果合同的一部分。预览和导出可以使用不同分辨率与调度策略，但不能交换步骤或使用含义不同的参数。

### 5.2 频率与区域原则

- 光线和肤色调整主要作用于低频信息；不能通过简单模糊整张脸得到均匀感。
- 皮肤平滑必须由皮肤适用性遮罩约束，并对眼睛、眉毛、嘴唇、鼻孔、发际线、胡须和高对比轮廓设保护区域。
- 细节回注必须来自当前原图或确定性分解结果，不使用生成式纹理。
- 所有遮罩采用软边界；任何调试可视化不得进入 Release 用户结果。
- 总强度为最终结果与原始局部结果之间的可解释混合，不允许供应商把 `0` 映射为仍有处理的隐藏基线。

### 5.3 安全强度

最终有效强度由三部分共同决定：

```text
effectiveStrength = min(userStrength, capabilitySafeMax, sampleSafeMax)
                    × faceConfidence
                    × inputQualityFactor
```

实际函数可以非线性，但必须满足：

- 低置信度、面部过小、严重遮挡、过曝和运动模糊只会降低或关闭处理，不能放大处理。
- 多张脸分别计算，不因主脸清晰就对低质量小脸使用同样强度。
- 无法证明瑕疵识别安全时，该子效果固定为关闭。
- 所有降级原因映射为稳定产品状态，不把模型或供应商原始错误暴露给 Flutter UI。

## 6. 能力边界与数据合同

### 6.1 供应商无关接口

纵切引入以下概念边界，而不是让业务层依赖某个 SDK 对象：

- `PortraitCapability`：当前平台是否支持分析、预览和原图导出，以及稳定的不可用原因。
- `PortraitAnalysisSession`：绑定一张应用自有输入与方向信息，持有原生分析结果和遮罩生命周期。
- `PortraitRetouchRecipe`：只保存用户允许持久化的版本、总强度与声明过的确定性子参数。
- `PortraitRenderResult`：纹理、尺寸、适用状态、降级状态和稳定错误，不包含供应商对象。

接口命名是规格概念，不要求按此直接创建类。正式编码前应以现有 `PhotoPreviewRenderer`、`PhotoExporter` 和 `ImagePipelineV1` 的相邻实现为基准设计最小演进。

### 6.2 Flutter 与原生层

Flutter 可以接收：

- 是否检测到适用人像；
- 可用/降级/失败状态；
- 可展示的稳定原因；
- 进度与 Texture handle。

Flutter 不接收：

- 完整皮肤、人像或五官遮罩；
- 人脸关键点数组、embedding 或可用于身份匹配的特征；
- 原始模型输出和供应商错误对象；
- 滑杆过程中的完整图片字节。

原生分析缓存只属于当前项目或渲染会话。项目删除、输入变化、能力版本变化或缓存过期后必须失效。

### 6.3 配方版本

- 不改变既有 `ImagePipelineV1` 已发布语义。
- 人像纵切进入实现时应新增版本化扩展或新版本，并声明迁移与未知字段拒绝规则。
- 配方保存的是可复现参数，不保存处理后的整张预览位图。
- 供应商版本、模型版本和效果资产版本必须参与缓存身份，但不得成为 Flutter 业务判断分支。

## 7. 固定质量样片集

### 7.1 样片来源

- 只使用获得明确测试与内部评审授权的成人照片。
- 每张样片记录授权范围、原始文件哈希、方向、像素尺寸、色彩空间、设备类型和拍摄条件。
- 原图、面部裁剪和人工标注不得提交公开仓库；仓库只保存忽略路径下的 manifest 示例和不可逆样片 ID。
- 竞品处理结果只用于内部对照，不作为训练数据，也不得提交或公开传播。

### 7.2 最小矩阵

第一轮至少 48 张授权样片，其中至少 36 张为单人成人质量样片，其余用于多人和负向安全验证：

| 维度 | 最低覆盖 |
| --- | --- |
| 肤色 | 从浅到深均有覆盖，避免只用单一肤色调参 |
| 光线 | 柔和日光、硬光、逆光、低照度、混合色温、局部过曝 |
| 面部方向 | 正脸、轻侧脸、明显侧脸、抬头、低头 |
| 皮肤状态 | 原本平滑、可见纹理、轻微泛红、痘印、雀斑、痣、胡须 |
| 外观 | 无妆、淡妆、明显妆容、眼镜、刘海、面部局部遮挡 |
| 图像质量 | 清晰、轻微运动模糊、高 ISO、前摄降噪、压缩输入 |
| 尺寸 | 常见 12 MP 与合同上限附近的大图 |

负向集至少覆盖：无人脸、雕像、海报/屏幕中的脸、宠物、严重遮挡、极小人脸、多人远景和不支持输入。负向集的目标不是“也要美化”，而是证明不会误处理或阻断编辑。

### 7.3 对照版本

每个候选至少生成：

- 原图；
- 映见候选的关闭、默认和较高安全强度；
- 竞品固定操作路径的结果，操作步骤和版本必须记录；
- 候选预览与候选原图导出。

评审图随机化文件名、顺序和候选身份。评审者不能只看美化后的单张图，必须能够切换原图与候选并放大检查皮肤和边界。

## 8. 质量验收

### 8.1 人工盲评量表

每张结果按 1–5 分独立评价：

1. **整体改善**：是否更精神、通透且适合直接使用；
2. **自然度**：是否存在明显处理感、假面或塑料感；
3. **身份保持**：是否仍然像本人，稳定特征是否被改变；
4. **纹理保护**：皮肤是否细腻但仍有真实纹理；
5. **肤色与光线**：是否均匀、健康且没有漂白、偏灰或高光炸裂；
6. **局部边界**：五官、发际线、胡须、眼镜和脸部边缘是否干净；
7. **非皮肤保护**：背景、衣物、头发和配饰是否没有误处理。

冻结候选前的最低门建议为：

- 至少 5 名评审者，结果匿名随机；
- `自然度`、`身份保持`、`局部边界`不得出现任一评审者给出的 1 分；
- `身份保持`中位数不低于 4.5；其余安全维度中位数不低于 4.0；
- 在原图确有可改善空间的样片上，候选相对原图的成对偏好率不低于 65%；
- 深色肤色、胡须、雀斑/痣、眼镜和明显妆容子集分别报告，不能用总体平均掩盖子集失败；
- 任一灾难性错误均阻断候选，不用其他样片高分抵消。

这些数值是第一轮冻结建议，不是已通过指标。样片授权和评审流程确认后才能转为正式门禁。

### 8.2 自动化正确性检查

- 相同输入、相同配方和相同能力版本产生确定性相同结果。
- 强度 `0` 的输出在允许的编码容差内等价于关闭人像处理。
- 预览和导出在方向、遮罩位置和效果趋势上保持一致。
- 输出方向、尺寸、裁剪和 sRGB 合同正确，原图不被覆盖。
- 使用人工保护区域检查眼睛、眉毛、嘴唇、发际线、胡须和背景的异常变化。
- 检查软遮罩边缘是否出现可见 halo、色边、棋盘格、黑边或未初始化纹理。
- 人脸缺失或能力不可用时，人像处理请求稳定降级，基础编辑与导出仍成功。

PSNR、SSIM、感知哈希或单一肤色差不能代表“变美”和“自然”，只能用于确定性、回归和非目标区域保护，不能代替盲评。

## 9. 性能与资源预算

正式预算必须在冻结的低、中、高档物理设备上测量。本轮 Spike 先使用以下建议值作为淘汰线：

| 指标 | 建议淘汰线 |
| --- | --- |
| 2,048 px 代理图分析到首个人像预览 | 中档机 P95 ≤ 1.5 s |
| 已有分析会话的强度更新 | UI 不阻塞，提交到原生 P95 ≤ 50 ms |
| 连续滑杆预览 | 中档机目标 30 FPS，不能持续掉到 20 FPS 以下 |
| 代理图分析与遮罩峰值增量内存 | 中档机目标 ≤ 160 MB |
| 前后台恢复 | 不复用失效 Surface/Texture，不崩溃、不显示旧人脸结果 |
| 离线能力 | 首次安装后断网仍能完成纵切，不触发云端任务 |

原图导出耗时、48 MP 峰值内存和温控属于后续原图执行 Spike 的独立门禁；代理图通过不能证明高清导出通过。

## 10. 隐私、安全与许可

- 默认离线处理，不上传照片、面部裁剪、关键点、遮罩或人脸特征。
- 不创建跨照片身份 ID，不做人脸识别、相似度比较或用户画像。
- 普通日志、Analytics、Crashlytics breadcrumb 和 Performance 属性禁止包含照片路径、人脸数量、关键点、肤色分类、遮罩统计或供应商原始错误。
- 调试样片和可视化遮罩保存在 Git 忽略的本地证据目录；不能使用真实用户照片作为默认测试资产。
- 候选 SDK 必须核对：端侧/云端边界、模型与二进制许可、商用范围、按设备或调用收费、离线许可失效行为、数据条款、最低系统版本、包体和 ABI 支持。
- “SDK 可调用”不等于“许可可上线”；许可、隐私、质量和双端一致性任一不通过都淘汰候选。

## 11. 候选路线与选择门

### 11.1 官方能力研究形成的当前边界

根据《[端侧人像能力一手资料研究](../research/portrait-retouch-foundation-research-2026-08-04.md)》，当前可以冻结以下边界，但不能冻结供应商：

- iOS 15 的 Vision 可以提供人脸关键点和整个人物 matte，不能为任意普通相册照片直接生成 face-skin mask；相机捕获时产生或文件已嵌入的 skin semantic matte 不能当作通用导入能力。
- Android ML Kit Face Mesh 可以提供至多两张脸的 468 点几何网格，Selfie Segmentation 可以提供人物/背景，但两者都不输出皮肤语义。
- MediaPipe SelfieMulticlass 是本轮官方资料中最接近需求的现成模型，能区分 face-skin、body-skin、hair、clothes 等类别；当前官方模型约 16.37 MB，官方 Pixel 6 整管线均值约为 CPU 217.76 ms、GPU 71.24 ms。其 256×256 边界质量、Preview 生命周期、最终运行库增量和目标设备 P95 均未验证。
- MediaPipe 官方说明 Tasks 输入在设备处理，但会发送 API 性能与使用指标。若无法验证其行为与“匿名诊断默认关闭、关闭后立即停止”兼容，该路线不得进入生产。
- 双边滤波、引导滤波和 Local Laplacian 只证明存在保边/细节处理算法基础，不证明已经解决皮肤识别、自然度或身份保护。

因此，“系统 API + 几何 ROI”可以作为安全回退和基线候选，但不能在盲评前直接宣称完成皮肤精修；“MediaPipe 皮肤解析”可以进入 Spike，但不能仅凭类别名称直接进入生产依赖。

### 11.2 路线比较

| 路线 | 要证明的优势 | 主要风险 | 进入生产前的证据 |
| --- | --- | --- | --- |
| 系统/官方端侧能力 + 自建处理 | 隐私边界清晰、供应商锁定较低 | 双端能力和遮罩质量不一致，算法调校成本高 | 双端可用范围、输出语义、样片分数、真机性能 |
| 自有端侧模型 + 自建处理 | 参数和效果可控，可形成长期资产 | 数据、训练、包体、设备适配和维护成本高 | 合法数据链、模型许可、子集公平性、量化后质量与性能 |
| 商业人像 SDK | 可能更快达到竞品入场质量 | 成本、黑盒、隐私、包体、供应商对象渗透和许可失效 | 同样片盲评、双端合同、报价与法律审查、离线失败演练 |
| 混合路线 | 分析和渲染可分别替换 | 版本组合与一致性复杂 | 供应商无关接口、版本矩阵、回退路径和回归样片 |

### 11.3 选择顺序

选择顺序固定为：

1. 先验证分析输出能否稳定约束皮肤区域和保护边界；
2. 再验证同一自建处理链在双端的可实现性；
3. 使用同一输入、强度和量表比较至少一个商业候选；
4. 计算包体、设备覆盖、许可、隐私和长期成本；
5. 只有通过质量门的路线才比较工程便利性。

## 12. 实施阶段与交付物

### 阶段 A：样片和评分门

- 建立授权样片 manifest、负向集和保护区域标注规范。
- 冻结盲评界面、随机化方法、评分量表和灾难性错误清单。
- 记录醒图或其他锁定竞品的固定操作路径，仅作为同任务对照。

### 阶段 B：分析能力 Spike

- 双端分别输出仅供本地调试的遮罩覆盖图。
- 评估正脸、侧脸、深浅肤色、胡须、眼镜、妆容和负向集。
- 不接产品 UI，不引入项目持久化，不上传任何样片。

### 阶段 C：单张效果 Spike

- 在 Android 现有 GLES3 代理图链上实现一个最小的区域受控处理序列。
- 建立 iOS 等义候选路径，不以 Flutter `ColorFilter` 作为正式人像回退。
- 只暴露总强度，保存关闭/默认/高安全强度结果供盲评。

### 阶段 D：候选冻结

- 在同一批样片、同一设备级别和同一量表上比较路线。
- 淘汰未通过自然度、身份、子集、安全、性能、许可或隐私门的候选。
- 记录 ADR：选择、拒绝理由、模型/SDK 版本、回退和重新评估条件。

### 阶段 E：产品纵切

- 把冻结能力接入版本化配方、预览、撤销、项目恢复和原图导出。
- 完成无人脸、低置信度、能力不可用、前后台和低内存降级。
- Profile/Release 物理设备复测后，才允许把纵切标记为完成。

## 13. 完成定义

本纵切只有同时满足以下条件才完成：

- 授权样片集和盲评协议已冻结；
- 至少一条双端可行路线通过人工质量门和自动正确性检查；
- 结果在可改善样片上具有明确偏好，同时没有身份改变和灾难性局部错误；
- Android 与 iOS 的参数语义一致，差异在冻结容差内；
- 关闭、降级、撤销、恢复、前后对比和原图导出完整可用；
- 默认路径断网可运行，未上传照片或面部数据；
- Profile/Release 物理设备满足冻结后的性能、内存和温控预算；
- 供应商许可、包体、平台覆盖和失败行为已验证；
- 文档、固定样片回归和发布门能够阻止后续算法或 SDK 升级静默降低人像质量。

## 14. 停止条件

出现以下任一情况，停止产品集成并回到候选评估：

- 只有高强度磨皮才能在盲评中获得“更好看”评价；
- 深色肤色、胡须、雀斑/痣、妆容或眼镜子集持续失败；
- 人脸边缘、五官和发际线无法稳定避免 halo 或漏抹；
- 预览好看但原图导出无法保持同一效果语义；
- 分析必须上传照片或面部数据才能达到最低质量；
- 双端只能依赖含义不同的黑盒参数，无法形成稳定配方；
- 商业许可、隐私条款、包体或离线失效行为不可接受；
- 中档目标设备无法达到冻结的响应与内存门。

## 15. 与现有工作的关系

- 现有 `ImagePipelineV1`、Android GLES3 Texture、项目恢复和导出 Adapter 是可复用技术接缝，不是人像质量证据。
- 本 Spec 将《映见 MVP Spec》中“最低可用自然人像能力”具体化；若两者冲突，以更严格的质量和隐私门为准，并应同步修订主 Spec。
- 三套推荐必须在本纵切通过后，才能把“自然精修”作为配方资产使用。
- 整组一致性必须在本纵切通过后，为每张照片独立计算人像安全强度和肤色保护；禁止机械复制同一磨皮强度。
- 48 MP 分块导出仍是正式 MVP 门，但不应先于人像效果价值验证消耗主要开发资源。
