# 静态任务与风格执行

## 目的

静态 `apply` 页面承载首页的优化照片、换风格和去背景 / 去杂物三个 `CreationTask`。它们都在选图前固定任务身份，选图后以固定顺序展示当前任务的 `CreationCapability`，且初始没有默认选择。只有用户点击的能力才能进入对应执行链；`creationIntent=apply` 不是用户可见的任务名，也不是能力或执行授权。旧 `apply` 草稿必须迁移为 `CreationTask.style`，以保留其风格语义。

本文重点定义本地确定性执行，尤其是用户明确选择官方风格、文字定风格、语音定风格或参考图风格后的应用路径：形成 `StyleDefinition` 和临时预览不等于静态提交；进入 `applyStyleReady` 后只显示“应用风格”这一个主 CTA。用户明确应用后，系统才把确定性投影解析为不可见参数配方并原子提交。优化和清理的本地能力可复用同一安全、预览、持久化与恢复边界，但不伪装成风格任务。

本路径只生成确定性静态结果，不展示“生成动态照片”入口。AI 修复、老照片修复、AI 风格重绘、生成式清理等静态生成能力，以及三项动态能力，都由用户从各自固定能力列表中明确选择后进入[独立生成管线](generation-pipeline.md)，不得塞入 `EditRecipe`。当前未实现的能力保持独立不可用，不能由本地近似效果冒充。

## 核心对象

### StyleDefinition

`StyleDefinition` 是“换风格”任务中确定性应用与静态风格生成共享的合同。静态应用只读取它的确定性应用投影；AI 风格重绘等静态风格生成只读取它的生成投影，两者不得互相嵌入执行状态。动态生成不读取 `StyleDefinition`，只绑定用户明确选择的动态方向。它至少包含：

- 稳定 ID、schema 版本和展示名称；
- 来源类型：内置、用户保存或 AI 提案；
- 有界、可序列化的语义效果集合；
- 支持的静态风格执行分支及各分支所需能力；
- 适用条件、所需平台能力和明确拒绝规则；
- 风格层替换身份；
- 定义来源与引擎兼容版本。

它不包含任意脚本、shader、自由提示词、`EditRecipe`、远程任务 ID、生成媒体或供应商对象。用户原始文字可以作为本地历史说明保留，但不能成为静态应用或静态风格生成结果的唯一执行依据。

AI 风格重绘在 presentation 层先把用户明确确认的草稿冻结为 `origin=aiRedraw` 的定义；只允许归一化排版空白，不做语义改写、补全或推荐。页面必须在云端同意 sheet 之前显示该定义的 `visualIntent` 与 revision。生成快照只从已确认定义的生成投影和内容摘要构建，不得读取可编辑文本框的即时值。

### StyleProposal

内置目录和 AI 都只产生 `StyleProposal`。只有用户先选择文字、语音或参考图风格并提交对应输入后，AI 才可以把该次输入翻译为提案；图片分析只能验证当前已选能力能否执行。AI 不能直接返回像素、任意渲染计划、供应商 payload，不能绕过目录增加能力，也不能推荐、排序、组合、替换或降级到另一能力。

提案绑定来源内容身份、当前风格基线、目录版本和幂等身份。任一身份过期时必须重新解析，不能自动合并到新状态。在“换风格”任务中，确定性应用投影还必须绑定当前编辑状态版本并进入 `EditingCore`。动态任务使用用户单独选择的动态方向，不读取或推导当前 `StyleDefinition`；静态应用会话也不负责切换任务或创建生成快照。

### StyleCommit

`StyleCommit` 记录已接受的定义、规范化编辑状态、稳定 `RenderPlan` 身份和来源状态版本。它只属于本地“应用风格”路径，是恢复、撤销、对比和静态导出的依据。AI 风格重绘等静态生成能力从同一 `SourcePhoto`、用户已选能力和已确认输入创建自己的来源快照，不要求存在 `StyleCommit`；动态生成另行绑定用户选择的动态方向。

## 执行流程

```text
home: choose 换风格
  → select image
  → explicitly choose 官方 / 文字 / 语音 / 参考图
  → choose or define style within that capability
  → resolve proposal
  → validate application projection
  → render temporary preview
  → applyStyleReady
  → 应用风格
  → validate transaction and compile RenderPlan
  → render final result
  → commit or reject
```

1. 用户先在首页选择“换风格”；presentation 固定 `CreationTask.style` 和 `creationIntent=apply`，再导入应用自有、只读来源及内容身份。进入页面时没有默认能力或默认风格。
2. 用户明确选择官方、文字、语音或参考图风格后，现成风格或已提交输入才产生提案；AI 风格重绘属于独立静态生成能力，不进入本地应用流程。
3. `EditingCore` 依据唯一元操作目录完成参数、目标、能力、冲突和状态版本校验。
4. 原生渲染器以版本化临时计划执行真实预览；占位图、静态缩略图或仅更新选中态不算成功，预览成功只进入 `applyStyleReady`。
5. `applyStyleReady` 只显示“应用风格”。用户明确选择后，确定性投影才绑定当前编辑状态，校验为事务并编译最终 `RenderPlan`。
6. 最终渲染与持久化成功后一次性创建 `StyleCommit`；失败保持最后一个安全状态并返回结构化原因。
7. 本流程不显示或处理生成 CTA；用户要创作动态作品时从首页进入独立“做动态效果”任务，静态会话不会因此创建事务或 `StyleCommit`。

## 替换与撤销语义

- 用户选择“应用”另一个风格时，原子替换上一风格拥有的操作地址，不把两个完整风格连续叠加。
- 风格之外、明确属于来源安全或兼容迁移的状态只能按目录规则保留，不由页面猜测合并。
- 一次风格应用形成一个撤销步骤；AI 风格定义和临时预览本身不进入静态历史。
- 撤销恢复上一个完整风格状态；长按或等价入口比较只读原图，不创建历史。
- 归零、中性风格和恢复原图必须严格可复现。

## AI 与隐私

- 用户选择官方风格时不调用 AI；用户选择文字、语音或参考图风格后，才可使用该能力约定的本地解释器或云端 Planner。
- 云端 Planner 需要的文字、语音、参考图或结构化数据必须在该能力内明确说明并取得确认；未确认不发送，也不上传原图、蒙版、人脸特征或本地路径。
- 若某类 AI 风格定义必须读取原图，必须另设明确授权、上传范围、删除和成本合同，不能复用另一能力的权限。
- AI 输出先经过与内置风格相同的定义校验和真实临时预览；只有用户选择“应用”后才进入确定性校验与原子提交。

## 失败与拒绝

- 不支持的能力、未知 schema、越界参数、目标失效和过期提案全部 fail closed。
- 用户已选择的 AI 能力不可用时，明确说明不可用并保留当前状态；不得自动切换为内置风格。
- 图片分析失败时拒绝当前执行并说明原因；不得自动改用所谓安全风格、中性结果或其他能力，也不得从文件名、路径或自由元数据猜测内容。
- 预览或持久化失败不得发布半应用状态；最后一个安全提交继续可见、可撤销、可导出。

## 验证合同

- 同一来源、编辑基线、`StyleDefinition`、目录版本和引擎能力生成稳定编辑状态与 `RenderPlan` ID。
- 依次应用不同风格时证明替换而非叠加，撤销恢复完整前态，重启恢复同一结果。
- AI 对抗测试覆盖未知能力、越界值、重复地址、提示注入、过期状态、取消、去重和日志隐私。
- 固定样片验证中性恒等、预览/导出同义、目标保护和不支持能力严格拒绝。
- 集成测试必须从生产首页“换风格”入口进入，证明进入时没有默认能力、选择前没有分析后执行或上传；用户明确选择官方风格及一个具体风格后保持 `CreationTask.style` 与 `creationIntent=apply`，`applyStyleReady` 只显示“应用风格”，并至少完成一次真实应用、风格切换与撤销。优化和清理分别从各自入口验证固定能力列表、无默认选择、真实可用性与静态结果；未实现能力必须保持独立不可用，不能自动改走本地近似能力。
