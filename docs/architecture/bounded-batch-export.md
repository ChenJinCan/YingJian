# 有界批量导出

## 用户合同

编辑页对 1–6 张项目提供一个批量导出终点。每张从应用自有的只读原图路径和项目的有效三层配方独立调用原生 `PhotoExporter`，不从屏幕预览、缩略图或上一张结果继续处理。

当前调度器固定单并发、按项目顺序执行。这是有意的内存上界：同一时刻只允许一个原生全分辨率导出进入运行态，不同时完整解码六张。未来可以依据物理设备数据提高并发，但必须先证明峰值内存和温控预算。

## 状态机

开始时，仅把目标项从 `notQueued`（首次）或 `failed/cancelled`（重试）变为 `queued`，然后项目进入 `exporting`。每张只沿以下路径前进：

```text
queued → running → saved | failed | cancelled
```

- 单项异常只把该项落为 `failed`，已保存和后续项目不回滚。
- 用户取消只阻止尚未开始的 `queued` 项；当前原生保存不被伪装成可逆操作。
- 重试只重新排队 `failed/cancelled`，不会重复导出已经 `saved` 的照片。
- 所有项终态后项目进入 `exported`，完成卡分别显示保存、失败和取消数量。
- 用户选择继续编辑时返回 `editing`；任何后续共享或单张改动会按既有规则把受影响项恢复为 `notQueued`。

逐张状态持久化在项目 JSON 中，但应用重启不会自动重放未确认的导出任务。若恢复时仍有 `queued/running`，它们统一安全落为 `cancelled`，已经 `saved` 的结果保持有效，并显示完成卡；之后必须由用户再次确认重试。

## 已实现证据

- 单元回归覆盖三张中一张失败、其他成功保留、只重试失败项。
- 单元回归覆盖第一张运行中取消，第一张保存、剩余两张取消。
- Widget 回归覆盖部分失败完成卡和只重试失败项。
- 原图导出仍复用 iOS Core Image / Android 原生导出接缝及同一 `effectiveRecipeFor(photoId)`。

## 仍未验证

- 12/24/48 MP 真实图像的三轮六张压力测试；
- iPhone Profile/Release 的时间、峰值内存、后台、低内存和温控；
- PhotoKit 单项保存处于不可逆阶段时的物理设备取消观察；
- HEIC/P3/EXIF 旋转和元数据矩阵的最终产物回查。

因此批量任务语义为 `implemented`，物理设备与最终图像合同仍为 `validation incomplete`。
