# ADR 0004：任务优先入口、风格创作与派生生成分流

- 状态：Superseded in part by [ADR 0005](0005-four-task-home.md)
- 保留范围：静态应用与派生生成的执行隔离、独立 ready 状态、原图与结果边界仍然有效；首页的两个用户入口已由四任务模型取代。
- 日期：2026-08-31
- 影响范围：主交互、静态编辑入口、AI 风格定义、派生媒体生成、项目状态与供应商 seam
- 取代范围：ADR 0003 中“手动、推荐、文字和语音作为并列可见入口”以及“整组编辑作为主线”的产品决定

## 背景

传统“分类 → 工具 → 参数”修图路径要求用户理解实现语言，无法形成映见的清晰优势。把“应用”和“生成”放在定好风格后的同一个页面，又会让用户到流程末端才选择原本就不同的任务，并让界面同时竞争两个大动作。

产品因此在首页先呈现两个任务入口：

```text
首页
  ├─ 图片应用 → 选图片 → 定风格 → applyStyleReady → 应用风格
  └─ 动起来   → 选图片 → 定风格 → motionStyleReady → 让图片动起来
```

静态风格应用与图片生成是架构上的兄弟 Module，却是 presentation 中从首页即分开的任务流。两者具有不同的确定性、成本、隐私、失败和恢复语义。若让二者共享就绪状态、结果按钮、`EditRecipe` 或任务状态，用户心智与技术状态都会互相污染；若把生成放在应用之后，用户又会被迫先提交不需要的静态结果。

## 决策

1. 首页以两个同级大入口先询问用户要完成的任务：“图片应用”和“动起来”。二者位于选图和定风格之前，不是定好风格后的并排结果按钮。
2. presentation 用 `creationIntent=apply|motion` 保持任务选择。该值只控制导航、状态与文案，不进入 `StyleDefinition`、静态配方、渲染计划、生成快照或供应商 payload。
3. 两条流程使用独立就绪状态：`applyStyleReady` 只显示“应用风格”，`motionStyleReady` 只显示“让图片动起来”。除首页的任务选择外，任何流程页面都不得同时展示两条任务的主 CTA。
4. 默认界面在任务流内以风格为唯一创作入口，不展示传统工具分类、参数矩阵或手动/推荐并列导航。
5. 内置选择与 AI 定义都产生分支无关、版本化的 `StyleDefinition`。AI 只有提案权；定义必须经过统一 schema、能力和安全校验，不得包含任意脚本、供应商 payload 或像素结果。
6. “应用风格”读取风格的确定性应用投影，并经过唯一能力目录、`EditingCore` 与真实预览；风格编译为不可见配方和 `RenderPlan`，成功后原子提交，并提供完整撤销、恢复原图和预览/导出同义。
7. 切换风格替换前一个风格层，不把多个完整风格隐式叠加。
8. 默认每条任务流一次围绕一张当前图片完成。多个独立草稿可以存在，但整组同步、批量范围和专业参数不作为首要心智。
9. “动起来”进入独立异步派生媒体管线，第一优先是 `image_motion`。生成不要求先应用、先创建 `StyleCommit` 或先静态导出。
10. 生成读取风格的规范化生成投影，从 `SourcePhoto + StyleDefinition` 直接创建不可变 `GenerationSourceSnapshot`，可包含专供生成的冻结参考渲染；生成请求、提示、供应商任务、进度和产物不得写入静态 `EditRecipe`、`EditingCore` 或 `RenderPlan`。
11. 生成必须由 `motionStyleReady` 的唯一 CTA 显式触发，并独立处理授权、上传、幂等、取消、重试、成本、恢复、产物校验和删除。失败或取消不得创建或改变静态提交。

## 保留的既有决定

- ADR 0001 的只读原图、输入、色彩、元数据和静态导出合同继续有效。
- ADR 0002 的版本化静态预览与导出 seam 继续有效。
- ADR 0003 的规范编辑状态、原子事务、唯一元操作目录、`EditingCore`、`RenderPlan`、历史恢复、平台能力拒绝和 AI 提案安全继续有效。

## 取舍

- 用户在首页多做一次明确的任务选择，换取后续每个页面只有一个目标和一个主 CTA。
- 用户获得更小、更清晰的选择面，但不再把所有专业参数作为默认可发现能力。
- 底层参数和元操作仍然存在，却成为风格执行语言而非产品导航。
- 静态应用和生成分成两个 Module 与两条 presentation 状态流，增加各自的会话状态、来源身份与任务持久化，但换取远程失败隔离、供应商可替换和成本可控。
- 生成结果不保证像静态配方一样确定性重放，因此必须保存来源、请求、模型和产物身份。

## 被拒绝的方案

- **继续扩充手动工具层级**：增加学习与选择成本，不能形成风格优先差异。
- **选完风格后同时展示“应用风格”和“让图片动起来”**：把两个不同任务推迟到流程末端决定，造成界面竞争和状态混用。
- **用一个 `styleReady` 根据按钮临时决定分支**：presentation 无法保证单一任务与单一 CTA，错误恢复也容易跨分支泄漏。
- **把 AI 风格作为另一套编辑状态**：会产生与内置风格不同的验证、撤销和导出真相。
- **把动画参数加入 `EditRecipe`**：把异步、非确定性供应商任务错误伪装成可重放静态效果。
- **静态应用后自动生成动画**：会在用户未确认时上传、计费或创建不需要的媒体。
- **让页面直接调用生成供应商**：供应商协议、错误和权限会扩散到 UI，无法统一恢复和测试。

## 验证要求

- 生产首页只展示“图片应用”和“动起来”两个大入口；进入任一任务后只需理解图片、风格和该任务唯一 CTA，不依赖传统参数分类。
- `creationIntent` 在选图、换图和定风格期间保持稳定；`applyStyleReady` 与 `motionStyleReady` 不可互换，且任何流程页面都不同时出现两条任务 CTA。
- 内置风格和 AI 风格走同一风格定义验证；“图片应用”流程只在用户选择“应用风格”时统一经过预览、提交、撤销、恢复和导出 Interface。
- 风格切换证明替换而非叠加；静态失败保持最后安全结果。
- `image_motion` 可直接从 `SourcePhoto + StyleDefinition` 创建，不依赖 `StyleCommit`；取消、失败、重试和重启恢复不创建或改变静态编辑状态。
- 序列化与日志检查证明生成字段未进入 `EditRecipe` 或 `RenderPlan`。
- 新增页面或路由时，通过生产首页导航的 `integration_test` 分别覆盖“图片应用”和“动起来”旅程，并断言每条流程只有自己的主 CTA。
